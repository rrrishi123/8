unix_socket CALLCHANNELwire

Not a new protocol — the same CALL and CHANNEL bytes, dialed over a unix-domain socket instead of TCP. No port, no network stack, just a path on disk. A unix socket carries no framing of its own, so it stays in the wire, not an adapter.

why there is no live button here

Browsers deliberately cannot open a unix socket — fetch() and WebSocket only speak http(s):// and ws(s):// over the network. Unix sockets are a local-process transport, so this one is proven in Go, not in a tab. That boundary is the point: unix sockets exist precisely to talk to something on the same machine with no port exposed.

the wire's URL forms
modeURLmaps to
CALLhttp+unix:///var/run/app.sock:/routehttpx.Do over net.Dial("unix",…)
CHANNELws+unix:///var/run/app.sock:/wswsx.Dial over net.Dial("unix",…)

everything up to the first : after the authority is the socket path; the rest is the request path.

where you actually use it
  • talk to dockerd at /var/run/docker.sock with no TCP exposure
  • a chromedriver / appium sidecar over a pipe
  • the 8 collector ↔ browser without opening a port on the box
How this is proven: the conformance test dials http+unix://…/ping (CALL) and ws+unix://…/ws (CHANNEL) against a real unix listener it owns — both halves, same bytes as TCP. See probeUnixSocket in http-mcp/cmd/mcp/transports_conformance_test.go. A browser can watch http and websocket; this is those same two atoms, just addressed by a filesystem path.
